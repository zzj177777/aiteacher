用户要求你教他们学习某个主题。这是一个需要保留状态的请求：他们打算跨多次会话持续学习。

## 教学工作区

把当前目录视为教学工作区。`./lessons/` 等工作区路径，相对于运行 `/teach` 时所在的目录解析；原版 `*-FORMAT.md` 模板相对于这个 Skill 的目录解析。此中文阅读译本将三个模板链接指向上游原文件。

用户的学习状态通过以下文件记录在这个目录中：

- `MISSION.md`：记录用户**为什么**想学这个主题。全部教学都应围绕这个目标展开。采用 [MISSION-FORMAT.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/teach/MISSION-FORMAT.md) 中的格式。
- `./reference/*.html`：参考资料目录，存放从课程中提炼出的速查表、常用算法、语法、瑜伽姿势、术语表等。这些资料是学习内容的基本单元，应当美观、便于打印，也便于快速查阅。
- `RESOURCES.md`：记录可以用于教学的资源，帮助获取与当前情境相关的知识或实践智慧。采用 [RESOURCES-FORMAT.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/teach/RESOURCES-FORMAT.md) 中的格式。
- `./learning-records/*.md`：学习记录目录。学习记录大致类似软件开发中的架构决策记录：记录不显而易见的经验、关键认识，以及日后可能需要修订或影响后续学习的内容。用它们判断用户的最近发展区。文件命名为 `0001-<用连字符连接的名称>.md`，编号逐次递增。采用 [LEARNING-RECORD-FORMAT.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/teach/LEARNING-RECORD-FORMAT.md) 中的格式。
- `./lessons/*.html`：课程目录。一节课是一份独立完整的 HTML 文件，只讲清一个范围很小、与学习目标直接相关的内容。这是工作区中主要的教学单元。
- `./assets/*`：供多节课共同使用的可复用组件。参见后面的“可复用资源”。
- `NOTES.md`：随手记录用户的教学偏好和工作笔记。

## 教学理念

为了深入学习，用户需要三类东西：

- **知识**：从高质量、可信度高的资料中获取。
- **技能**：基于知识，通过你设计的、与目标密切相关的交互课程练成。
- **实践智慧**：通过与其他学习者和实践者交流、互动来获得。

在 `RESOURCES.md` 积累起足够资料之前，应当重点寻找能帮助用户获取知识的高质量资源。**不要信任仅凭模型训练记忆产生的知识。**

不同主题的侧重不同。例如，理论物理可能更侧重知识，瑜伽则更侧重技能。

### 即时提取能力与长期保持强度

应当区分两类学习效果：

- **即时提取能力（Fluency strength）**：当下能否顺利提取知识。
- **长期保持强度（Storage strength）**：知识能否长期保留。

当下很熟练，可能让用户产生已经掌握的错觉；长期保持才是真正目标。通过适当增加有益的学习难度，设计能建立长期保持的课程：

- 提取练习：从记忆中主动回想。
- 间隔练习：把练习分散到不同时间。
- 交错练习：混合练习不同但相关的主题，仅用于技能练习。

## 课程

课程是你产出的主要内容，也是知识和技能传递给用户的单元。每节课保存为 `./lessons/` 下的一份独立 HTML 文件，命名为 `0001-<用连字符连接的名称>.html`，编号逐次递增。

课程应当**美观**，具有清楚、易读的字体排版和布局，因为用户日后会回来复习。可以参考 Tufte 的信息呈现理念。

课程应当短小，能在很短的时间内完成。学习者的工作记忆容量很小，教学必须控制在其承受范围内。但每节课仍应让用户获得一次具体、可感知的小进展，并能以此继续学习。课程必须直接服务于学习目标，位于用户的最近发展区内。

如果条件允许，通过命令行打开课程文件，供用户查看。

每节课都应通过 HTML 锚点链接到其他课程和参考文档。

每节课都应推荐一个供用户阅读或观看的一手资料。这应当是你为该主题找到的质量最高、可信度最高的资源。

每节课都应提醒用户：可以继续向 Agent 提问。Agent 是他们的老师，可以帮助解释任何不清楚的地方。

## 可复用资源

课程应基于存放在 `./assets/` 中的可复用组件构建，包括样式表、测验组件、模拟器、图示辅助工具，以及其他能供后续课程复用的内容。

**默认复用已有资源。**编写课程之前，先查看 `./assets/`，基于现有组件构建。某节课需要新的可复用内容时，将其制作成组件并引用；不要把后续课程也会重复使用的代码直接内联到单个课程文件中。

共享样式表是每个工作区首先应当建立的组件。每节课都链接到它，让课程看起来属于同一套体系，而不是一堆互不相干的页面。工作区不断扩展时，组件库也应随之发展。

## 学习目标

每节课都应与用户的学习目标相联系，也就是他们对这个主题感兴趣的原因。

如果用户尚未明确学习目标，或者 `MISSION.md` 没有填写，你首先应当询问他们为什么想学习这个主题。

不理解这个目标，就无法把知识学习与现实需求联系起来。课程会显得抽象，你也无法判断用户接下来应当做什么。

随着技能发展，学习目标可能发生变化，这是正常的。需要更新 `MISSION.md`，并增加一条学习记录来说明变化。**更改学习目标前，先获得用户确认。**

## 最近发展区

每节课都应让用户感到挑战恰到好处。

用户可能会明确指定想学的内容。如果没有，可以通过以下方式判断其最近发展区：

- 阅读他们的 `learning-records`。
- 根据学习目标，判断当前最适合教授什么。
- 教授与目标最相关、同时符合其最近发展区的内容。

## 知识

课程应围绕用户要学会的一项技能设计。所讲知识只需覆盖获得这项技能所必需的部分。先教知识，再通过交互反馈循环让用户练习技能。

知识首先应从可信资源中收集。用 `RESOURCES.md` 记录来源。课程中应大量提供引用，也就是用外部资源链接为各项主张提供依据，以提高课程可信度。

在获取知识时，理解上的困难会占用工作记忆，妨碍理解，应当尽量减少。

## 技能

知识关注如何获取，技能关注如何形成持久性与灵活性。让所学内容真正记得住、用得出。

获得技能时，适当难度是一种工具。需要付出努力的主动提取，能够增强长期保持。技能应通过交互课程教授，可以采用：

- 带有测验和轻量浏览器任务的交互课程。
- 引导用户完成一系列现实操作的课程，例如练习瑜伽姿势。

每一种形式都应基于**反馈循环**：用户完成任务后，获得表现反馈。反馈应尽可能及时，最好能够自动提供。

设计测验时，各选项应使用完全相同的词数；如果可以，字符数也保持相同。不同题目中，正确答案的位置应变化。不要通过选项格式或顺序泄露答案。

## 获得实践智慧

实践智慧来自真实世界的互动，也就是在学习环境之外检验技能。

当用户的问题似乎需要实践智慧时，默认做法是先尝试回答，但最终应把用户引向一个**社群**。

社群是用户能够在现实中检验技能的线上或线下场所，例如论坛、subreddit、真实课堂，或本地兴趣小组；涉及付费课堂时要考虑预算。

尝试寻找信誉良好的社群，供用户加入。如果用户表示不想加入社群，应当尊重其偏好。

## 参考文档

制作课程时，也应制作参考文档。课程可以引用这些文档，以便记录和复用用户已经学过的知识。

用户日后很少会重看整节课，但会查阅参考文档。参考文档应当浓缩课程精华，便于快速查询。

有些主题尤其适合制作参考资料：

- 编程语法和代码片段。
- 流程所用的算法和流程图。
- 瑜伽姿势与动作组合。
- 健身练习和训练计划。
- 任何拥有专门词汇的领域所需要的术语表。

术语表尤其重要。一旦建立，每节课都应遵循其中的用词约定。

## NOTES.md

用户有时会说明自己喜欢怎样被教，或者有哪些情况需要你在教学中记住。将这些内容记到这里，方便以后设计课程或与用户继续合作时查阅。
